# 1.4 — Processes

## What I learned

**What a process is**
A process is a running instance of a program. One program (e.g. `bash`) can have many separate running processes at once, each with its own PID (process ID), independent of each other.

**`ps aux`**
Lists all currently running processes as a one-time snapshot:
- `a` = show processes for all users
- `u` = user-friendly format (owner, CPU%, memory%)
- `x` = include processes with no controlling terminal (background/system processes)

Key columns: `PID` (unique process ID), `%CPU`, `%MEM`, `STAT` (process state), `COMMAND` (what's actually running).

**STAT column letters**
- `S` = sleeping (waiting, not actively using CPU — very common, not a problem)
- `R` = running right now
- `l` = multi-threaded
- `+` = running in the foreground of its terminal
- `Z` = zombie (finished process whose exit status hasn't been collected yet)

**Piping and filtering with grep**
```bash
ps aux | grep sola
```
The pipe (`|`) takes the output of the command on the left and feeds it as input to the command on the right — instead of printing to screen, it gets passed along for further processing.

**Gotcha: grep matching itself**
Running `grep sola` causes grep's own command line (which contains the word "sola") to show up in its own results. To exclude it:
```bash
ps aux | grep sola | grep -v grep
```
`-v` = invert match — show lines that do NOT match the given pattern. This was the first time we covered exclusion/inversion in this course.

I also tried a "clever" alternative — `grep "sol[a]"` — which changes the literal text of the grep command so it no longer contains "sola." This worked for the COMMAND column, but still failed in my case, because my username is also `sola`, and grep scans the entire line (including the USER column), not just the command portion. `grep -v grep` is more reliable because it doesn't depend on incidental string matches like a username — it targets the one thing that's actually always true: only grep's own process line contains the literal word "grep."

## top / htop
`top` = live, auto-refreshing view of processes (vs `ps aux`'s one-time snapshot). `htop` = friendlier version — color bars, per-core CPU view by default, scrollable, easier process killing (F9).

## kill
`kill PID` — sends SIGTERM (signal 15): a polite request to shut down gracefully.
`kill -9 PID` — sends SIGKILL (signal 9): immediate forced termination, no cleanup. Last resort only — risky on things like databases mid-write.

## Background processes (&)
Appending `&` to a command runs it in the background, returning control of the terminal immediately instead of waiting for it to finish. Tested with `sleep 300 &`, found its PID via `ps aux | grep sleep`, killed it with `kill <PID>` — confirmed by `[1]+ Terminated`.

This is the foundation of how real servers stay running — a process tied to a terminal session dies when that session closes. Real production services use `systemd` (or tools like `nohup`, `pm2`) instead of a bare `&`, so they survive independent of any one engineer's session.
