# 1.8 — Logs

## What I learned

Logs are records of what a program/service did — errors, warnings, status, events. The single most important habit in DevOps: when something breaks, logs are almost always the first place to check why.

```bash
journalctl -u <service>       # logs for a specific systemd service
journalctl -u <service> -f    # follow live, like tail -f
journalctl -xe                # recent logs, extra detail, jump to end
ls /var/log                   # traditional plain-text log files
```

Compared `systemctl status cron` (shows a few recent log lines automatically) vs `journalctl -u cron -n 20` (shows a longer history) — same underlying events, but journalctl gave enough history to spot a real pattern.

**Real finding:** noticed an 11-hour gap in cron's hourly logs (13:17 → 00:17 next day). This wasn't a bug — my WSL machine simply wasn't running during that window. Cron only runs while the machine is on; it doesn't "catch up" on missed runs. This is exactly why production servers (always-on) rely on cron confidently, while a laptop dev environment will always show gaps.
