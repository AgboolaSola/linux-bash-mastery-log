# 4.7 — Script Arguments

## What I learned

Scripts accept arguments directly from the command line, without needing `read`:
```bash
./myscript.sh hello world
```
```bash
$0    # the script's own name
$1 $2 # individual arguments, in order
$#    # total number of arguments passed
$@    # all arguments as a list
```

Confirmed all of these behave correctly with 0, 2, and 3 arguments passed — `$1`/`$2` empty and `$#` = 0 when nothing is passed, incrementing correctly as more arguments are added.

**Why this matters over `read`:** `read` needs a human present to type an answer — useless for automation (cron jobs, CI/CD, scheduled tasks run with zero humans present). Arguments let everything needed be specified at the moment the script is launched, so it can run fully unattended.

## Exit codes
```bash
exit 1    # non-zero = failure
exit 0    # convention: success
```
Checked with `$?` immediately after running a command — shows the exit code of the last command that ran. Confirmed my script's `exit 1` (triggered when no filename argument was given) correctly showed up as `1` via `echo $?`.

**Real relevance:** cron jobs, CI/CD pipelines, and monitoring tools check a script's exit code programmatically to know if it succeeded or failed — not by reading printed text. A script that fails silently without setting a proper exit code can cause a real problem to go undetected (e.g. a failed backup that nothing catches).

## Built a real combined example
```bash
if [ "$#" -eq 0 ]; then
    echo "Error: no filename provided."
    exit 1
fi

filename=$1
if [ -f "$filename" ]; then
    echo "✓ $filename exists"
else
    echo "✗ $filename does not exist"
fi
```
Tested with zero arguments (correct error + exit 1), an existing file (correct success message), and a nonexistent file (correct failure message, still exit 0 since the script itself ran successfully — only the *check* failed, not the script).
