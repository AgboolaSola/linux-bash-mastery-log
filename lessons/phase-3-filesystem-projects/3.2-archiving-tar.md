# 3.2 — Archiving with tar

## What I learned

```bash
tar -czvf archive-name.tar.gz folder/   # c=create, z=gzip compress, v=verbose, f=filename
tar -xzvf archive-name.tar.gz            # x=extract
```
`f` always comes last, immediately before the filename.

Used command substitution to auto-name the archive with today's date:
```bash
tar -czvf logs-backup-$(date +%Y%m%d).tar.gz logs/
```

**Real compression result:** 84K raw folder → 452 bytes actual file size (`ls -lh`) / 4.0K on-disk (`du -h`) — over 99% smaller, because the log content was highly repetitive text, which gzip compresses very effectively.

**du vs ls -lh discrepancy explained:** `ls -lh` shows exact logical file size; `du -h` shows actual disk space consumed, rounded up to the nearest block (commonly 4KB) — a tiny file still occupies one full block, since disks can't allocate partial blocks. Both are "correct," just answering different questions; `du` is what matters for real disk-full investigations.

**Tested full delete + restore cycle:** deleted `logs/` entirely (`rm -r`), then restored it completely from the archive (`tar -xzvf`) — confirmed all 20 files came back intact. Proves archiving before deleting is a genuine safety net, not just a formality: logs get deleted to free disk space, but may still be needed later for debugging/compliance, and an archive keeps that option open.
