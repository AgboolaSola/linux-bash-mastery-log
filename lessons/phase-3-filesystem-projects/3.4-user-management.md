# 3.4 — Managing Users

## What I learned

```bash
sudo adduser <username>              # create a new user (interactive, sets password)
sudo deluser <username>               # remove a user
sudo usermod -aG <group> <username>   # add an existing user to a group
groups <username>                      # show a user's group memberships
sudo groupadd <groupname>              # create a new group
```

Created `testuser` — got UID `1001` automatically, confirming the ≥1000 human-user convention from Phase 2 (`sola` was 1000, next available number assigned sequentially). Ubuntu's `adduser` also creates a matching personal group per user by default (group name = username), separate from any shared groups.

**Critical flag: `-a` in `usermod -aG`**
- `-a` = append (add to a group without touching existing memberships)
- Omitting `-a` and running plain `usermod -G group user` **replaces** all of that user's existing group memberships with only the new one — silently, no warning, no confirmation.

**Real-world danger:** an existing user in `docker`, `sudo`, `deploy-team` etc. could lose all of that access in one command if `-a` is forgotten — breaking their scripts/pipeline/deploy access with no obvious cause. A recurring theme: Linux tools trust the exact command typed and rarely warn before doing something destructive — `-a` is the entire difference between "add" and "replace."

## Real DevOps use
Giving a new team member exactly the access they need (e.g. a `developers` group) without granting full root power — least privilege applied to real onboarding.
